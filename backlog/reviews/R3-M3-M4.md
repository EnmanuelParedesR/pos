Line numbers refer to that commit.

What this change does: M3 adds physical registers, shifts (one register plus one cashier), cash movements (cash in, withdrawals and expenses with a supervisor), a blind closing count by denominations, and X and Z reports. M4 adds the sale in one transaction (totals and ITBIS engine, mixed payments, e-CF, stock out, cash into the shift, outbox, audit), held carts, receipt reprint, void inside the shift and partial returns with a credit note. It also adds e-NCF ranges with gap-free numbering and a simulated signer. ("e-NCF" is the fiscal number printed on each receipt. A "credit note" (e-CF 34) is the fiscal document that cancels all or part of an earlier receipt.)

## Must fix

1. **A double-clicked void, or a void and a return at the same time, pays the money back twice** (`Features/AnularYDevolver.cs:L41-48`, `L121-133`, `L142-160`, `VentasDbContext.cs:L26-51`)
   - **What this is:** Void and return both read the sale and its lines first. Then they lock the shift row and check `Estado` and `CantidadDevuelta` on what they read. `Venta` and `LineaVenta` have no concurrency token, so EF saves them with "last writer wins".
   - **Problem:** On SQL Server the read happens before any lock, so the data can be stale when the checks run. These cases happen:
     - **Double void, same shift.** A supervisor double-taps "Anular". Both requests read `Completada`. The second one waits on the shift lock, then runs with its stale copy. It issues a second credit note, puts the stock back a second time, and writes a second set of `AnulacionCobro` rows. Expected cash drops by the sale amount twice, so the cashier can take that amount from the drawer and the blind count still balances.
     - **Void plus return.** The void locks the sale's shift. The return locks today's shift. When those are different shifts, nothing makes them wait for each other. Both commit: the void reverses the full payment, and the return refunds part of it again.
     - **Two returns of the same line.** Register 1 and register 2 each return 1 of 3 units. Both read `CantidadDevuelta = 0`, both pass, both refund a third of the line, and the saved value is 1 instead of 2 (a "lost update"). Later, two more units can still be returned. Stock gets 4 units back for 3 sold.

     A retry of the same `DevolucionId` is only stopped by the primary key at the end. The register then gets a 409 "Duplicado" for a return that did go through.
   - **Fix:** Lock the sale row before you read it, in both handlers. Add `public int Version { get; set; }` to `Venta`. At the start of `AnularVenta` and `DevolverVenta`, run `db.Ventas.Where(v => v.Id == id).ExecuteUpdateAsync(s => s.SetProperty(v => v.Version, v => v.Version + 1))` and read the sale only after that. The sale row then becomes the first lock (sale row → shift → fiscal → stock → audit). New sales never lock existing sale rows, so this order adds no deadlock. In `DevolverVenta`, check the `DevolucionId` again after the lock, the same way `RegistrarVenta` does (L78). Add an integration test that fires two voids at once (expect one 200 and one `Ventas.YaAnulada`), a void and a return at once, and two returns of 1 of 3 at once (expect `CantidadDevuelta = 2` and refunds that add up to two thirds of the line). They only prove something on SQL Server. On SQLite they still check the final state.
   - **If we skip it:** Refunds and voids can be done twice, and that is the easiest theft at a register. The counts and Z reports then hide it.

2. **A cashier can sell anything at any price by sending a "price label" amount** (`Features/RegistrarVenta.cs:L26-27`, `L91-101`, `L104-106`)
   - **What this is:** For a scale price label, the register sends `MontoEtiqueta`, and the server uses it as the fixed line total. The quantity is derived from it (`monto / precio`).
   - **Problem:** The server never reads the label. `CodigoEtiqueta` is optional and is not parsed, and nothing checks that it matches the product or the amount. A request with `ProductoId = chuleta, Cantidad = 5, MontoEtiqueta = 100.00` charges RD$ 100 for any weight. The price is still the list price, so `precio != lista` is false, the below-cost check uses the list price, and no supervisor is asked. This is a price change without `ventas.cambiar-precio`. It only takes an edited request, and R1 already treated scripted HTTP from a register as a real threat.
   - **Fix:** The server must read the label itself. Expose the existing parser through the catalog contract, for example `ICatalogoConsultas.LeerEtiquetaAsync(string codigo)` returning `(ProductoId, Peso?, Monto?)` and built on `EtiquetaBalanza.Leer`. In `RegistrarVenta`, when `CodigoEtiqueta` is set, parse it, return 409 if the product differs, and take the amount (or the weight) from the label. Drop `MontoEtiqueta` from the request. A line with a fixed amount and no label code becomes impossible. Change `Una_etiqueta_de_precio_cobra_lo_que_dice_la_etiqueta` to send only the code, and add a test that sends the real code with a lower amount and expects the label's amount (or `Ventas.TotalCambio`).
   - **If we skip it:** The price permission and the supervisor check in TK-040 can be bypassed with one field.

## Should fix

3. **A card sale can be refunded in cash** (`Features/AnularYDevolver.cs:L110-111`, `L174`)
   - **Problem:** The return's `Medio` is free. Example: an accomplice pays RD$ 5,000 by card, then returns it, and the cashier refunds RD$ 5,000 cash from the drawer. That turns a stolen card into cash. The supervisor authorization is bound to the sale and the permission only, so the supervisor does not see which refund method was chosen.
   - **Fix:** In `DevolverVenta`, limit each method to what the sale took in that method, minus what earlier returns already gave back in it. The sale's `PagoVenta` rows and the `Devoluciones` rows already have the data. Return a validation error otherwise. Add one test: a card sale, then a cash refund, is rejected.
   - **If we skip it:** Returns become a way to cash out cards.

4. **Discount and below-cost checks look at the whole sale, not at each line** (`Features/RegistrarVenta.cs:L98-100`, `L110`)
   - **Problem:**
     - The cap compares the sale's total discount to its gross (`PorcentajeDescuento`). In a RD$ 2,000 sale, a 100 % discount on a RD$ 150 bottle is 7.5 % of the sale, under the default 10 % cap. So the cashier can give away one item per big sale with no supervisor.
     - `bajoCosto` uses the unit price before discounts. A 60 % line discount on chuleta (cost 110, price 165) sells it far below cost with no check.
     - One `ventas.cambiar-precio` authorization covers every line of the sale. A supervisor who approves one damaged item has also approved any price on every other line.
   - **Fix:** After `Calculadora.Calcular`, check each line: `t.Lineas[i].Descuento / t.Lineas[i].Bruto * 100 > tope` adds `ventas.descuento-mayor`, and `(t.Lineas[i].Total - t.Lineas[i].Itbis) < costo × cantidad` adds `ventas.cambiar-precio`. Then delete the price-only `bajoCosto` line. For the third point, the cheapest fix is to show the supervisor the expected total when they authorize and store it with the authorization. That is optional, but write it down as a known limit.
   - **If we skip it:** The discount cap stops big discounts, but not small, regular giveaways.

5. **The blind count can be probed with one cash-drop authorization** (`Features/Turnos.cs:L151`, `CajaModule.cs:L91`)
   - **What this is:** A withdrawal or expense larger than the expected cash fails with `Caja.SinEfectivo`. The supervisor authorization is consumed inside the transaction.
   - **Problem:** When the handler fails, the transaction rolls back, and the authorization is not used up. Within its 2 minutes, a cashier with a script can send withdrawals of 30,000, 29,950, 29,900 and so on. Each one fails without using the authorization, until the first one passes. That tells them the expected cash within RD$ 50. The withdrawal that passes is a normal cash drop. They then pocket the overage before the blind close. A cash refund (`RegistrarReembolsoAsync`) leaks the same way.
   - **Fix:** Delete both `SinEfectivo` checks (2 lines plus the error). The supervisor physically collects a withdrawal, so a typo is caught by hand. A wrong amount also shows up as a negative expected cash in the X report. Update `Un_retiro_pide_supervisor_y_no_saca_mas_de_lo_que_hay`.
   - **If we skip it:** The blind closing (a main anti-theft feature in `funcionalidades-v1.md`) can be beaten by anyone who can script HTTP.

6. **Centavos make every blind close show a difference** (`Domain/Calculadora.cs:L87-111`, `Domain/Caja.cs:L62-65` in Caja)
   - **Problem:** Line totals have centavos (2.355 lb × 165 = 388.58). Change is computed to the centavo (the integration test gives RD$ 494.25 of change). Dominican cashiers have no coins below RD$ 1, and the count accepts nothing below RD$ 1 (`Denominaciones.Dop`). So expected cash almost never equals any amount that can be counted. Every shift then closes with a small difference that is not theft. That noise teaches supervisors to ignore differences.
   - **Fix:** This needs a product decision, but the smallest version is: in `Pagos.Aplicar`, round the cash change down to whole pesos, and record the kept centavos as a separate cash movement (for example a `Redondeo` type in Caja). Then expected cash is always whole pesos. The e-CF total does not change. Add a unit test: 505.75 paid with 1,000 gives 494 of change and 0.25 of rounding.
   - **If we skip it:** The cash count cannot show real shortages under about RD$ 10 a day.

7. **Credit-note lines do not add up when the original line had a discount** (`Features/AnularYDevolver.cs:L158`)
   - **Problem:** For a return, the e-CF line is `(Cantidad, PrecioUnitario, Descuento = 0, MontoItem = monto)`, but `monto` is already net of the line and global discount. Example: 2 × 100 with 20 % off is a line total of 160. Returning 1 produces Cantidad 1, Precio 100, Descuento 0, MontoItem 80. DGII validates MontoItem = Precio × Cantidad − Descuento, so this would be rejected. The void path is fine (it passes `l.Descuento`).
   - **Fix:** Pass `Descuento = Dinero.Redondear(lv.PrecioUnitario * l.Cantidad) - monto` (for a price-label line, use the proportional gross). Assert in the partial-return test that every credit-note line satisfies `Precio × Cantidad − Descuento = MontoItem`, within one centavo.
   - **If we skip it:** Every credit note for a discounted line is stored with wrong amounts, and the real provider rejects them.

8. **Simulated e-CF are stored as "pending", the state the real sender will pick up** (`Domain/Fiscal.cs:L25`, `FiscalModule.cs:L100-105`)
   - **Problem:** `FirmadorSimulado` signs with a hash and adds a `<FirmaSimulada>` element, but the document gets `Estado = Pendiente`. The TK-051 worker will send pending documents by `FechaLimiteEnvioUtc`. On the day the real signer and worker are turned on, every simulated document from the pilot goes out to the provider. In the best case they are rejected and fill the rejection inbox. In the worst case they are sent with e-NCF numbers that are also in real ranges.
   - **Fix:** Add `EstadoEnvio.Simulado`. Set it when the signer is the simulated one (for example a `bool EsSimulado` on `IEcfFirmador`). The worker reads only `Pendiente`. That is 3 lines now, and it avoids a data clean-up later.
   - **If we skip it:** Turning on the real provider needs a manual SQL clean-up on every pilot store first.

9. **What the real e-CF provider will need is not in the fiscal contract or not validated** (`Toki.Fiscal.Contracts/Contracts.cs:L11-13`, `FiscalModule.cs:L88-99`, `Features/RegistrarVenta.cs:L56-59`)
   - **Problem:** Every caller builds `DocumentoAEmitir`, so missing fields mean changing Ventas (and Compras later) when the real signer arrives. These are concrete:
     - **RNC of the store:** if the shop settings have no RNC, `EmitirAsync` still issues documents with an empty `RNCEmisor` and an empty `RncEmisor=` in the QR.
     - **Consumo (32) of RD$ 250,000 or more:** these must identify the buyer (RNC or cédula). The validator asks for the RNC only for type 31.
     - **Credit notes:** there is no modification code (1 = cancels the whole document for a void, 3 = corrects amounts for a return). The original document's date can be looked up from `ENcfModificado`, but the code cannot. `EmitirAsync` also accepts a 34 without `ENcfModificado`.
     - **Payment type:** there is no "cash or credit" field. Fiado sales (TK-071) will need it.
   - **Fix:** In `EmitirAsync`, return `Fiscal.SinRncEmisor` when `negocio.Rnc` is empty, and `Fiscal.ReferenciaRequerida` for a 34 without `ENcfModificado`. In the sale validator, require `RncCliente` when the total is ≥ 250,000. The total is only known on the server, so check it in the handler after `Calcular`. Add `CodigoModificacion` and `TipoPago` to `DocumentoAEmitir` now, with defaults, while there are only three callers.
   - **If we skip it:** The real provider work (TK-055) also has to change the Ventas slices, and documents from a store without an RNC are unusable.

10. **Some names can exceed the 200-character default, so a sale fails only on SQL Server** (`Features/RegistrarVenta.cs:L59`, `Toki.Inventario/InventarioModule.cs:L46`, `VentasDbContext.cs:L45-51`)
    - **Problem:** A presentation line's description is `"{product} ({presentation})"`. Product names allow 150 characters and presentation names allow 60, so it can be 213 characters. `LineaVenta.Descripcion` is `nvarchar(200)`. `NombreCliente` has no limit on a consumo sale, and it is stored in `Venta.ClienteNombre` and `DocumentoFiscal.NombreComprador`. On SQL Server either one fails with "String or binary data would be truncated", which becomes a 500. SQLite accepts it. This is R2 #9 again.
    - **Fix:** Give `LineaVenta.Descripcion` `HasMaxLength(220)`, and apply `MaximumLength(150)` to `NombreCliente` for every receipt type.
    - **If we skip it:** A register shows a 500 for one product or one customer name, but only in the store.

11. **The riskiest money and concurrency paths have no test that fails when they break** (`tests/Toki.IntegrationTests/Ventas/VentasTests.cs`, `tests/Toki.IntegrationTests/Caja/CajaTests.cs`, `tests/Toki.UnitTests/Ventas/CalculadoraTests.cs`)
    - **What this is:** There are 12 good HTTP tests for sales and 6 for Caja, plus 13 unit tests for the engine, payments and the Z report. They check stock, expected cash, the audit chain and the kardex.
    - **Problem:** These behaviors have no test:
      - Everything in 1 (parallel void and return), 2 (a tampered label), 3 (the refund method) and 4 (per-line discount and below cost).
      - **Presentations:** a sale of a presentation (Factor 12) moves 12 units of stock, prints the presentation name, and returns proportionally.
      - **Wholesale:** `Nivel = Mayorista` uses `PrecioMayorista` and needs `ventas.cambiar-precio`, and passes with an authorization.
      - **Fractional units:** 1.5 bottles is rejected for a sale and for a return.
      - **Last-piece return:** a line of 3 for 100.00 is returned 1 + 1 + 1, giving 33.33 + 33.33 + 33.34, with ITBIS adding up to the line's ITBIS.
      - **Sequences:** a range running out moves to the next range. An expired range is skipped. No range gives `Fiscal.SinSecuencia` and saves nothing. A credit note stores `ENcfModificado`. The 80 % and 30-day alerts work.
      - **Shifts:** a sale on a closed shift gives `Caja.TurnoCerrado`. A sale on another cashier's shift gives `Caja.TurnoAjeno`. Z numbers go up per register.
      - **Retry of the same `DevolucionId`:** it returns the same answer.
      - **Engine unit tests:** a global % discount over mixed ITBIS rates, a price-label line with a line discount, and a 100 % discount.
    - **Fix:** One test per item. Run the parallel tests from 1 in the SQL Server CI job. The e2e suite (TK-095) must start the real process on SQL Server and run a whole store day:
      - install, catalog with presentations and scale labels, e-NCF ranges for 31, 32 and 34
      - 3 registers open shifts and sell the same weighed products at the same time (multi-line, opposite scan orders, mixed payments, price labels read by the server)
      - a credit-fiscal sale with RNC, a held cart resumed on the same register, a discount over the cap with a supervisor, a wholesale sale
      - a void (including a double tap), a partial return on another register's shift, and a return of the last piece
      - a cash drop, an expense, and a closing while sales are still committing
      - a blind close with denominations, then the Z report
      - a restart of the process in the middle of the day
      - at the end: for every register, expected cash equals float + cash sales − cash voids − cash refunds + cash in − withdrawals − expenses. The sum of the kardex equals stock. e-NCF numbers per type have no gap and no duplicate. Each document's total equals its sale or return. The audit chain verifies. No request returned 500.
    - **If we skip it:** Findings 1 to 4 went unnoticed for this reason, and the next ones will too.

## Nice to have

12. **A return's ITBIS can differ from the line's ITBIS by a centavo** (`Features/AnularYDevolver.cs:L152-155`)
    - **Problem:** The last piece takes the remaining amount, but its ITBIS is recomputed from that amount and not taken as the remaining ITBIS. After 1 + 1 + 1 returns, the three ITBIS values can add up to the line's ITBIS ± 0.01, so a 607 report will be a centavo off.
    - **Fix:** For the last piece, `itbis = lv.Itbis - itbisYaDevuelto`. Sum `Itbis` next to `Total` in the `yaDevuelto` query.

13. **Held carts are not tied to their shift or cashier** (`Features/Consultas.cs:L110-134`, `L146-151`)
    - **Problem:** `PUT /en-espera` with an existing id overwrites another register's cart. `DELETE /en-espera/{id}` deletes any cart. `GET ?turnoId=` lists any shift's carts. Carts of closed shifts are never removed.
    - **Fix:** In `Guardar` and `Quitar`, match `TurnoId` too (`e.Id == c.Id && e.TurnoId == turnoId`) after `ObtenerTurnoAbiertoAsync`, and delete the shift's carts in `CerrarTurno`.

14. **The QR link uses the same format for every receipt type** (`FiscalModule.cs:L155-162`)
    - **Problem:** DGII's printed format uses a shorter link for consumo receipts under RD$ 250,000 (`ConsultaTimbreFC`, with only RNC emisor, e-NCF, total and security code), and the full `ConsultaTimbre` for the rest. It also has separate test and certification hosts. Today every receipt gets the full production link.
    - **Fix:** Choose the link by type and amount when the real provider is set up (TK-055), and take the host from configuration. Check it against the current DGII format document.

15. **Sequence alerts are per range and only seen in the back office** (`Features/Secuencias.cs:L65-73`)
    - **Problem:** A used-up or expired range keeps `AlertaUso`/`AlertaVencimiento` = true forever, even after a new range is loaded, so the owner learns to ignore it. The registers never see it, so the first sign is that every register stops with `Fiscal.SinSecuencia`.
    - **Fix:** Compute the alert per type over the ranges that can still be used (available numbers < 20 % of the active total, or the last one expires in ≤ 30 days). Return a flag in `GET /api/caja/turnos/actual` so the register shows a banner.

16. **Every sale holds the store-wide fiscal lock while it updates stock** (`Features/RegistrarVenta.cs:L120-126`, `AnularYDevolver.cs:L50-58`, `L164-173`)
    - **Problem:** The e-NCF row for type 32 is one row for the whole store. It is locked from `ReservarAsync` until commit, which includes about 3 queries per line in Inventario. A 40-line sale on register 1 makes registers 2 and 3 wait for all of it. A sale that fails with `SinExistencia` also reserved a number first.
    - **Fix:** Issue the e-CF after stock and payments in all three handlers (order: sale row → shift → stock → fiscal → audit, the same for everyone). The lock is then held only for the signing and the inserts.

17. **A retry with the same `VentaId` and a different cart gets the old sale back** (`Features/RegistrarVenta.cs:L73`, `L78`)
    - **Problem:** If a register bug reuses an id, the cashier collects money for the new cart and nothing is recorded.
    - **Fix:** When the saved total differs from `c.TotalEsperado`, return 409 `Ventas.IdRepetido` instead of the saved sale.

18. **The shift is not tied to the register device** (`CajaModule.cs:L66-78`, `Features/Turnos.cs:L73-75`)
    - **Problem:** `arquitectura-v1-vsa.md` §2.2 checks the shift with `usuario.DispositivoId`. The code does not. A cashier on register 2 can open "Caja 1" (wrong pick in a list) or sell on their shift from any paired device. The Z report of Caja 1 then counts register 2's drawer.
    - **Fix:** Store the `DispositivoId` on `CajaFisica` when it is assigned. Check it in `AbrirTurno` and `ObtenerTurnoAbiertoAsync` (supervisors excepted).

19. **The same cashier can open two shifts at once** (`Features/Turnos.cs:L74-75`)
    - **Problem:** `CajeroConTurno` is a check-then-insert. Only the register has a unique index. Two opens from two devices at the same moment both pass.
    - **Fix:** Add a filtered unique index on `CajeroId` where `CerradoUtc IS NULL`, like `IX_Turnos_CajaAbierta`.

20. **Lean**
    - `Totales.ItbisDe` (`Domain/Calculadora.cs:L20`) and `ENcf.EsValido` (`Fiscal/Domain/Fiscal.cs:L58-59`) are never called. Delete them.
    - `Secuencia.Activa` is never set to false, and no endpoint changes it. Delete it, or add the "deactivate range" action if the owner needs it.
    - `RegistrarMovimiento` casts `(CajaOperaciones)operaciones` (`Features/Turnos.cs:L150`). Register `CajaOperaciones` as itself (as Inventario does with `MovimientosInventario`) and inject it directly.
    - With 2 done, `MontoEtiqueta` goes away from the request. With 5 done, both `SinEfectivo` checks and the error go away.
