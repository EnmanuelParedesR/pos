# R4 · Review of M6 (Compras) and M7 (Clientes y fiado) (commits e63f6a6 and aeeaa81)

Scope: `src/Modules/Purchasing/**`, `src/Modules/Customers/**`, and where Ventas and Caja call them (`Ventas/Features/RegistrarVenta.cs`, `Ventas/Features/AnularYDevolver.cs`, `Caja/CajaModule.cs` `RegistrarAbonoClienteAsync`), plus their tests (`tests/Toki.IntegrationTests/Compras`, `tests/Toki.IntegrationTests/Clientes`, `tests/Toki.UnitTests`). I also read `MovimientosInventario` (stock and average cost), `CostoPromedio`, the transaction and authorization decorators, the audit writer, `CuadreTurno` and `ReporteZ` to follow the real flow.
Load assumed: the same as R3. One store, the main PC as the server on SQL Server Express (READ COMMITTED), 3 registers selling at the same time, one back-office user (sometimes with two browser tabs). Local tests run on SQLite, which runs one write transaction at a time, so races never show up locally.
State checked: at HEAD (3db63e0, after the R3 fixes), `dotnet build Toki.slnx` is clean (0 warnings, 0 errors), and `dotnet test --solution Toki.slnx` passes 157 of 157 on SQLite. The SQL Server suite was not run here. The working tree has uncommitted Ventas reporting work (`VentasModule.cs`, `VentasReportes.cs`, `Ventas.Contracts/Reportes.cs`, ADR 0004). That work is outside this review. The files in scope have no uncommitted changes, and line numbers refer to HEAD.

What this change does: M6 adds suppliers and purchase drafts. Applying a draft puts stock in, updates the weighted average cost, and creates a payable when the purchase is on credit. It also adds purchase voids, expenses with an NCF, supplier payments applied to the oldest invoices first, a supplier statement and payables aging. M7 adds customers (quick add from the register, price level, credit limit) and fiado: a charge per credit sale, the limit checked again under a customer lock, and a supervisor to go over it. Customers can pay at the register: the money goes into the shift and pays the oldest charges first. Returns can leave a balance in favor that pays for later sales. There are statements and receivables aging, and hooks so a sale void or return updates the customer's account.

## Must fix

1. **A double-clicked purchase void takes the stock out twice, and a void that races an apply can leave a "voided" purchase with stock and an open payable** (`Features/ComprasMercancia.cs:L169-187`, `L50-90`, `ComprasModule.cs:L31-32`)
   - **What this is:** `AnularCompra` reads the purchase first. Then it locks the supplier row, takes the stock out, and saves `Estado = Anulada` on the copy it read. `Compra` has no concurrency token, so EF saves it with "last writer wins".
   - **Problem:** On SQL Server the read takes no lock, so the copy can be stale when the checks run. These cases happen:
     - **Double void.** The owner double-clicks "Anular". Both requests read `Aplicada`. The second waits on the supplier lock, then runs with its stale copy. It takes the stock out a second time (`soloConExistencia` only stops it when stock is short, and a butcher shop usually has stock). It also writes a second `AnulacionCompra` kardex row and a second `CompraAnuladaV1`.
     - **Void and apply at the same time** (two tabs). The void reads `Borrador`, so it skips the stock and payable part. The apply claims the draft, puts the stock in, creates the payable and commits. Then the void saves `Anulada` over it. The purchase list says "voided", but the stock stayed and the payable is open, so the owner pays an invoice he thinks is voided. The same pair can also deadlock: the void takes the audit head and then the purchase row (at `SaveChanges`), and the apply takes them in the other order.
     - **Edit and apply at the same time.** `PUT /api/compras/{id}` reads the draft. The apply puts in stock for the old lines. Then the PUT replaces the lines and totals. The purchase then shows lines and a total that match neither the kardex nor the payable.
   - **Fix:** Lock the purchase row before reading it, the same way R3 did for sales. Add `public int Version { get; set; }` to `Compra` and a `BloquearCompraAsync(id)` (an `ExecuteUpdate` of `Version + 1`, then the read with lines), like `VentasDbContext.BloquearVentaAsync`. Call it first in `AnularCompra` and in the update path of `GuardarCompra`, and check `Estado` only after it. The lock order is then purchase row → supplier → stock → audit, and `AplicarCompra` already takes the purchase row first with its claim. Add integration tests: two voids at once (one 204 and one `Compras.YaAnulada`, with stock going down once), and a void and an apply at once (the end state is either applied with a payable, or voided with no stock and no payable).
   - **If we skip it:** A double click on "Anular" silently loses stock, and the payables list can show debts for invoices the owner voided.

2. **A voided purchase stays in the average cost, and since R3 that blocks sales** (`Features/ComprasMercancia.cs:L155`, `L180-181`, `Toki.Inventory/InventarioModule.cs:L80-104`, `L171-172`, `Ventas/Features/RegistrarVenta.cs:L135-137`)
   - **What this is:** The `shortcut:` comment says the void does not recompute the average cost and that "the next purchase corrects it".
   - **Problem:** The usual reason to void a purchase is a typo, and the next purchase does not correct it. Example: there are 50 lb of chuleta at a cost of 100. The owner receives 100 lb and types 1,000 instead of 100, so the average becomes (50×100 + 100×1,000) / 150 = 700. He voids it, and the stock goes back to 50 lb, but the cost stays at 700. Since R3, each sale line is checked against cost (`RegistrarVenta.cs:L135-137`). Every chuleta sale at 165 is now "below cost", so it needs `ventas.cambiar-precio` and a supervisor. When he enters the correct purchase (100 lb at 100), the cost only drops to (50×700 + 100×100) / 150 = 300, which is still below the price. The cost cannot be fixed by hand, because `ActualizarProducto` has no `Costo` field. The kardex also records the void's stock-out at 700 instead of 1,000, so the inventory value is off by RD$ 30,000 for good.
   - **Fix:** Reverse the average on a void. In `SalidaAsync`, add a flag (for example `revertirCosto`) and keep each line's cost through `Agrupar`, which drops it today (use the weighted cost of the group). After the decrement, let `total` be the stock in all warehouses. If `total > 0`, compute `costo = ((total + q) × costoActual − q × costoEntrada) / total` and save it when it is positive. Otherwise leave the cost as it is, because most of that purchase was already sold. Write the kardex row at the purchase cost. `AnularCompra` passes `l.CostoUnitario / l.Factor`. Then delete the shortcut comment. Add a unit test for the formula and an integration test: apply the typo, void it, and expect the cost back at 100.
   - **If we skip it:** One typo stops the counter for that product, and the only workaround is a fake purchase.

3. **A customer payment at the register is not idempotent** (`Features/Clientes.cs:L119`, `L135-163`, `Caja/CajaModule.cs:L115-121`)
   - **What this is:** `RegistrarAbono` creates its id on the server. It adds the money to the shift and applies it to the oldest charges. ("Idempotent" means that sending the same request twice has the same effect as sending it once.)
   - **Problem:** Sales and returns take their id from the register, so a retry after a Wi-Fi drop gets the saved answer back (`arquitectura-v1-vsa.md` §5.3). The abono has no such id. Example: the cashier records a 500 payment, the answer is lost, and the register retries (or the cashier taps again). Now there are two abonos. The debt goes down by 1,000 although only 500 came in. Expected cash is 500 higher, so the blind count shows a 500 shortage the cashier did not cause. A second abono that would go over the debt is rejected, so the double only happens silently on partial payments, which are the common case.
   - **Fix:** Add `AbonoId` (a GUID v7 from the register) to `Body` and `Command`. Use it as `AbonoFiado.Id` and as the Caja `ReferenciaId`. If an abono with that id exists, return its answer, and check again after the shift lock, exactly like `VentaId` in `RegistrarVenta.cs:L76-81`. Test: post the same abono twice and expect the same response, one cash movement and the debt down once.
   - **If we skip it:** Each time the network blinks during a payment, the store either loses cash or wipes part of a debt.

## Should fix

4. **The same supplier invoice can be entered twice** (`Features/ComprasMercancia.cs:L53-54`, `L119-142`, `Features/GastosYPagos.cs:L45`, `L102-128`, `ComprasModule.cs:L62`, `L80`)
   - **Problem:** The NCF check is a check-then-insert, and the `(SuplidorId, Ncf)` indexes are not unique. `POST /api/compras` and `POST /api/compras/gastos` take no id from the client. So a double click on "Guardar" can create two drafts with the same NCF, or two expenses and two payables. `AplicarCompra` does not check the NCF again, so both drafts can be applied, which puts the stock in twice and creates two payables. A purchase and an expense with the same NCF are also both accepted, and both would go into the 606. `POST /api/compras/pagos` has no id either, so a double click pays twice when the debt is big enough.
   - **Fix:** Add filtered unique indexes: Compras `(SuplidorId, Ncf)` where `[Estado] <> 'Anulada'`, and Gastos `(SuplidorId, Ncf)` where `[Anulado] = 0`. The transaction decorator already turns a unique violation into 409 `Duplicado`. In both handlers, also check the other table for the same NCF. Let the three POSTs take their `Id` from the client and return the saved answer on a retry (§5.3 already lists "compra" as an aggregate whose id comes from the client).
   - **If we skip it:** A double click can double the stock and the payables, and the 606 can get duplicate rows.

5. **Expenses, supplier payments and customer payments cannot be voided** (`Domain/Compras.cs:L100`, `Features/GastosYPagos.cs`, `Features/Clientes.cs:L117-175`)
   - **Problem:** `Gasto.Anulado` is never set, and there is no endpoint for it. A typo on an expense (40,000 instead of 4,000) stays as a payable and a 606 row forever, and its NCF stays taken, so the correct expense cannot be entered. The same goes for a supplier payment (10,000 typed for 1,000, so the invoices look paid) and for an abono at the register (5,000 typed for 500, so the debt drops by 5,000 and the blind count is 4,500 short). Only purchases and sales can be voided.
   - **Fix:** Mark records as voided and never delete them, as with sales. `AnularGasto`: lock the supplier, refuse it when the payable has payments (like `AnularCompra`), and set `Anulado` on the expense and on its payable. `AnularPagoSuplidor`: lock the supplier, set `Anulado` on the payment, and leave the applications of voided payments out of `AbiertasAsync`. `AnularAbono`: only while the shift is open, with a supervisor. It writes the reverse Caja movement, sets `Anulado` on the abono, and leaves its applications out of `CargosAbiertosAsync`. Add one test per void.
   - **If we skip it:** Every typo needs a database edit. That is the "balances kept by hand" problem from the old system (`funcionalidades-v1.md` §1).

6. **After a partly paid fiado sale is voided, the customer statement shows a negative debt** (`Features/Clientes.cs:L190-197`, `ClientesModule.cs:L140-149`)
   - **Problem:** Example: a fiado sale of 1,000, then an abono of 400, then the sale is voided in the same shift. The void marks the charge `Anulado` and moves the 400 already paid to balance in favor. The statement leaves out voided charges but keeps every abono. Its only line is "Abono 400", the running debt is −400, the header says `Deuda = -400` and `SaldoFavor = 400`. The customer card (`ObtenerAsync`) says `Deuda = 0`. So the statement counts the 400 twice, once as negative debt and once as balance in favor.
   - **Fix:** Take the header `Deuda` from `CargosAbiertosAsync`. In the lines, show a voided charge as its charge plus an "Anulada" line, and show the `CargoAnuladoPagado` movement as "Pasa a saldo a favor" (+400). The running debt then ends at 0. Test this exact case.
   - **If we skip it:** The statement the store prints for the customer disagrees with the screen.

7. **Cash customer payments bring centavos into the drawer** (`Features/Clientes.cs:L126-128`)
   - **Problem:** R3 #6 made cash sales come in whole pesos so expected cash is always an amount that can be counted. Fiado debts still carry centavos (for example 388.58). When a customer pays all of it in cash, the abono is 388.58, so expected cash gets 58 centavos that no count can match. Typing 389 instead is rejected with `AbonoMayorQueDeuda`. Every shift with such an abono closes with a small difference.
   - **Fix:** For `Efectivo`, accept only whole pesos. Apply `min(monto, deuda)` to the debt, and record any rest under RD$ 1 as `Redondeo`, the same movement sales use. A rest of RD$ 1 or more is still rejected. Test: a debt of 388.58 paid with 389 cash leaves the debt at 0 and expected cash 389 higher.
   - **If we skip it:** The noise in the blind count that R3 removed for sales comes back through abonos.

8. **A cashier can unblock a customer the owner blocked** (`Features/Clientes.cs:L48-50`, `Toki.Identity/Domain/Identidad.cs:L28`)
   - **Problem:** The Cajero role has `clientes.gestionar` so it can quick-add customers. On an update, the guard only covers `LimiteCredito` and `Nivel`. Example: the owner deactivates a customer who does not pay. A cashier sends a `PUT` with `Activo = true` and can then sell to them on fiado again, up to the old limit, with no supervisor. `DiasCredito` can also be changed without `fiado.gestionar`.
   - **Fix:** Add `Activo` to the fields that need `fiado.gestionar` (the `credito` check on L48), and add `DiasCredito` too if it stays (see 19). Test: a cashier's `PUT` with `Activo = true` on a deactivated customer returns `Clientes.SinPermisoCredito`.
   - **If we skip it:** Blocking a debtor only works if the cashiers cooperate.

9. **A credit to the account becomes balance in favor while the customer still owes** (`ClientesModule.cs:L148`, `L154-172`, `Features/Clientes.cs:L127`)
   - **Problem:** `AcreditarDevolucion` only pays down that one sale's charge, and the rest goes to balance in favor even when other charges are open. Example: a customer owes 2,000 from August. Today he buys 500 in cash and returns it to his account. He gets 500 in favor while the 2,000 keeps aging into 61–90 days. `RegistrarAbono` does not accept `SaldoFavor` as a payment method, so the two can never be netted. The only way to use the 500 is to buy more. The void path (L148) does the same with the part already paid. TK-071 says payments go to the oldest invoices.
   - **Fix:** After that sale's own charge, apply what is left to the other open charges, oldest first (the loop from `RegistrarAbono`). Only the remainder becomes balance in favor. Do the same in `AnularVentaAsync`. Test the example above.
   - **If we skip it:** The aging report and collection calls show debts that the store has in fact already paid back to the customer.

10. **Paying a supplier in cash from the drawer needs two entries that do not know about each other** (`Features/GastosYPagos.cs:L83-129`, `Caja/Domain/Caja.cs:L41`)
    - **Problem:** Caja has a withdrawal reason `PagoSuplidor`, and Compras has `PagarSuplidor` with `Medio = Efectivo`, but the two are not linked. Example: the distributor's truck is paid 5,000 from the drawer for last week's credit invoice. If the cashier records a Caja withdrawal, the drawer balances, but the payable stays open and the owner may later pay it again by transfer. If the owner records a Compras payment, the payable is right, but the drawer is 5,000 short at the close.
    - **Fix:** Add an optional `TurnoId` to `PagarSuplidor`. With `Efectivo` and a `TurnoId`, call a new `ICajaOperaciones.RegistrarPagoSuplidorAsync(turnoId, pagoId, monto)` in the same transaction. It writes the withdrawal with reason `PagoSuplidor` and needs `caja.retirar` or a supervisor, like `RegistrarAbonoClienteAsync` does for customers. Lock order: shift → supplier → audit.
    - **If we skip it:** Suppliers get paid twice, and nobody notices until the supplier's statement disagrees.

11. **Purchase totals are computed by Toki, never taken from the invoice** (`Domain/Compras.cs:L46-57`)
    - **Problem:** `Recalcular` computes and rounds ITBIS line by line. Many supplier systems compute ITBIS on the invoice subtotal, so a 3-line invoice can differ by RD$ 0.01 to 0.03. The payable is then a centavo below the printed invoice, so paying the printed amount fails with `PagoMayorQueDeuda`. The ITBIS that goes into the 606 also will not match the supplier's 607, and DGII cross-checks the two. Expenses already let the user type the subtotal and ITBIS. Purchases have no field for the invoice's own figures.
    - **Fix:** Add `ItbisFactura` and `TotalFactura` to the draft. Accept them when they are within RD$ 1 of the computed values, and use them for the payable and the 606. Costs stay per line. Test a 3-line invoice that differs by one centavo.
    - **If we skip it:** Payables keep centavo leftovers, and the 606 does not match every month.

12. **Buying a presentation fails on SQL Server only** (`ComprasModule.cs:L72-76`, `Features/ComprasMercancia.cs:L73`)
    - **Problem:** `LineaCompra.Descripcion` takes the catalog name `"{product} ({presentation})"`, which can be up to 213 characters, but the column has the 200-character default. R3 #10 fixed this for `LineaVenta` (220) but not for this copy. SQLite accepts it. SQL Server fails with "String or binary data would be truncated", and the user sees a 500. This is the third time (R2 #9, R3 #10).
    - **Fix:** Set `HasMaxLength(220)` on `LineaCompra.Descripcion`. Add a test to the SQL Server job that buys a presentation with the longest allowed names.
    - **If we skip it:** That purchase only fails in the store.

13. **Open balances read the whole history on every call** (`ComprasModule.cs:L35-43`, `ClientesModule.cs:L38-47`, `Features/GastosYPagos.cs:L178-187`, `Features/Clientes.cs:L215-224`)
    - **Problem:** `AbiertasAsync` and `CargosAbiertosAsync` read every charge the account ever had, paid ones included, and then send all their ids back in `ids.Contains(...)`. A regular colmado customer with 2 or 3 fiado sales a day has about 2,000 charges after two years, and this runs inside every sale to that customer. If EF Core 10 sends that list as separate parameters (its new default for collection parameters, as far as I know), SQL Server's limit of 2,100 parameters will make the sale fail, and only for the best customers. The aging endpoints also run two queries for each customer or supplier.
    - **Fix:** Use one query that computes the paid amount in SQL and keeps only charges with a balance. For example: `from c in Cargos where c.ClienteId == id && !c.Anulado let pagado = Aplicaciones.Where(a => a.CargoId == c.Id).Sum(a => (decimal?)a.Monto) ?? 0 where c.Monto > pagado orderby c.FechaUtc select new { c, Saldo = c.Monto - pagado }`. Do the same for payables. The aging reports can run that query once without the customer filter and group the results in memory.
    - **If we skip it:** The register keeps getting slower for regular customers, and on SQL Server it may fail outright.

14. **The riskiest money and concurrency paths have no test that fails when they break** (`tests/Toki.IntegrationTests/Compras/ComprasTests.cs`, `tests/Toki.IntegrationTests/Clientes/ClientesTests.cs`)
    - **What this is:** There are 7 good HTTP tests for Compras and 8 for Clientes. They cover the average cost, buying by the box, a repeated NCF, oldest-first payments, voids with stock, expenses, the fiado limit with a supervisor, abonos into the shift, a voided fiado sale, a return to the account, wholesale prices and the cashier's credit permission.
    - **Problem:** These behaviors have no test:
      - Everything in 1 (double void, void and apply at once, edit and apply at once), 2 (a typo then a void brings the cost back), 3 (a repeated abono), 6, 7, 8 and 9.
      - **Customer lock (SQL Server job):** two registers sell on fiado to the same customer when the limit left covers only one sale (expect one 201 and one `Clientes.LimiteExcedido`). Two registers spend the same balance in favor (expect one `Clientes.SinSaldoFavor`). An abono and a fiado sale run at the same time and the debt still adds up.
      - **Voids and returns:** voiding a sale paid with balance in favor gives the balance back (`AnulacionUso` has no test). Voiding a partly paid fiado sale moves the paid part to balance in favor (`CargoAnuladoPagado` has no test). A cash refund of a fiado sale is rejected (`Ventas.MedioExcedido`).
      - **Aging with a fake clock:** a charge at 23:30 local time (03:30 UTC the next day) lands in the right business day. Test the edges 30/31, 60/61 and 90/91. A payable due today is "por vencer", and one due yesterday is in 1–30.
      - **Payments:** a supplier payment to chosen invoices (`Cuentas`). A payment of exactly the whole debt. The final balance of each statement equals its aging total.
      - **Purchases:** a credit purchase with its own `DiasCredito`. An invoice with 18 %, 16 % and exempt lines (a unit test of `Recalcular`). A purchase into a second warehouse updates the average over all warehouses. A purchase from an inactive supplier is rejected.
      - **Permissions:** a cashier cannot raise the limit or set Mayorista on an existing customer (only creating one is tested). A cashier cannot open `/api/clientes/por-cobrar`.
      - `tests/Toki.UnitTests` has no test at all for Compras or Clientes.
    - **Fix:** One test per item, and run the parallel ones in the SQL Server CI job. The e2e store day (TK-095) should add these steps:
      - before opening: credit and cash purchases (one by the box), so the day's sales use the new average cost
      - a fiado sale over the limit with a supervisor, an abono in cash and one by card, and a return to the account
      - a void of a fiado sale, a purchase typo that is then voided, and a supplier payment
      - at the end: for every customer, charges minus applications = the debt on the card = the statement's final balance = the aging total. The same check for every supplier with payables. Expected cash includes cash abonos. The kardex sum equals stock. The product's cost after the voided typo equals its cost before. The audit chain verifies. No request returned 500.
    - **If we skip it:** Findings 1 to 3 went unnoticed for this reason, and the next ones will too.

## Nice to have

15. **Card and transfer abonos are missing from the Z report's per-method totals** (`Caja/Domain/ReporteZ.cs:L22`, `L37`)
    - **Problem:** `PorMedio` only counts sales, voids and refunds. `AbonosClientes` is a single number with all methods mixed. The card terminal's batch total is then higher than the Z report's card total by the amount of card abonos, and the cashier cannot explain the gap.
    - **Fix:** Include `AbonoCliente` movements in `PorMedio` (an `Abonos` column), or split `AbonosClientes` by method.

16. **Dates and the supplier's RNC are not validated** (`Features/ComprasMercancia.cs:L28-43`, `Features/GastosYPagos.cs:L23-35`, `L90-97`)
    - **Problem:** If a client leaves out `FechaFactura`, `Fecha` or the payment's `Fecha`, it binds as 0001-01-01, and a date far in the future is also accepted. Statements and aging then sort and age these wrongly. Purchases and expenses always carry an NCF, so they all go into the 606, which needs the supplier's RNC or cédula, but a supplier without an RNC is accepted.
    - **Fix:** Require the dates, and reject any date later than tomorrow. Return a validation error in `GuardarCompra` and `RegistrarGasto` when the supplier has no RNC.

17. **Edits take the row lock after the audit head** (`Features/Clientes.cs:L46-65`, `Features/Suplidores.cs:L37-46`)
    - **Problem:** `GuardarCliente` writes the audit record (which locks the audit head) and only updates the customer row at `SaveChanges`. A fiado sale or abono for the same customer takes these two locks in the other order: customer, then audit. When both run at once, they deadlock, and one of them gets 409 `Ocupado`. `GuardarSuplidor` and `PagarSuplidor` have the same problem with the supplier row.
    - **Fix:** On an update, call `BloquearAsync(id)` (or `BloquearSuplidorAsync`) before anything else, so the audit head stays the last lock taken.

18. **Inactive customers cannot be found again** (`Features/Clientes.cs:L99`)
    - **Problem:** `GET /api/clientes` only returns active customers. A deactivated customer can only be reactivated by someone who knows their id.
    - **Fix:** Add `?inactivos=true`, and allow it only with `fiado.gestionar`.

The other option is to use `Vence` in the aging, as payables do. Choose one.
    - `Aplicaciones.Local` in `CargosAbiertosAsync` (`ClientesModule.cs:L44`) and the `Local` part of `SaldoFavorAsync` (L51) are not needed by any current caller, because each request reads each customer's balance only once. The first one would also double count if applications were ever loaded with tracking. Delete both.
