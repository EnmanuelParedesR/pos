# R1 · Review of M0 + M1 (commit f553167)

Scope: `src/BuildingBlocks/**`, `src/Modules/Identity/**`, `src/Hosts/Abastalia.Host.Local/**`, `tests/**`, `Directory.*.props`, `.github/workflows/ci.yml`.
Load assumed: one store, the main PC as server, about 3 registers sending requests at the same time, plus one or two back-office users. Production database is SQL Server Express; local tests run on SQLite.
State checked: `dotnet build Abastalia.slnx` is clean (0 warnings, 0 errors). `dotnet test` passes 32 of 32 tests on SQLite (unit, integration, architecture). The SQL Server suite was not run (no Docker on this machine).

What this change does: It builds the backend skeleton. That means the command pipeline (validation, then one shared transaction, then the supervisor check, then the handler), one shared connection for every module's DbContext, the outbox, and a hash-chained audit log. It also adds the Identidad module: install, PIN login with lockout, users and roles, pairing and revoking registers, and one-time supervisor authorizations, with HTTP integration tests on SQLite and, in CI, SQL Server.

## Must fix

1. **PIN lockout can be bypassed with parallel requests on SQL Server** (`Features/Sesiones.cs:L45-54`, `Features/AutorizarSupervisor.cs:L40-49`, `Persistence/IdentidadDbContext.cs:L25-30`)
   - **What this is:** A failed PIN adds 1 to `Usuario.IntentosFallidos`. At 5 failures the user is locked for 5 minutes, and the time doubles after that.
   - **Problem:** The handler reads the user, checks the PIN in memory, and saves the new count. The row has no concurrency token. On SQL Server (READ COMMITTED), 50 wrong PINs sent at the same moment all read `IntentosFallidos = 0` and all write `1`, so only one try is counted. A cashier who is logged in can use `POST /api/identidad/autorizaciones` this way to guess the supervisor's 4-digit PIN about 100 times faster than the lockout allows, and then approve their own voids. SQLite runs the whole transaction under a write lock (`BEGIN IMMEDIATE`), so the local tests can never show this.
   - **Fix:** Mark the counter as a concurrency token: `b.Property(u => u.IntentosFallidos).IsConcurrencyToken();`. A parallel attempt that loses the race then gets `DbUpdateConcurrencyException`. The transaction decorator already turns that into a 409 and rolls back, so the losing request learns nothing about the PIN. Add a CI test that sends about 20 parallel wrong PINs and asserts that the user ends up locked.
   - **If we skip it:** The supervisor PIN, which guards voids, cash withdrawals and big discounts, can be brute-forced from the register by anyone who knows how to script HTTP.

2. **Dates without a time-zone kind are shifted by the server's own time zone** (`Persistence/ModuleDbContext.cs:L29-31`, `Abastalia.SharedKernel/Dinero.cs:L18-19`, `tests/.../SharedKernelTests.cs:L216-223`)
   - **What this is:** Every `DateTime` column goes through `UtcConverter`. `DiaNegocio.RangoUtc` returns the UTC range of a business day, and reports will use it.
   - **Problem:** `RangoUtc` returns values with `DateTimeKind.Unspecified`. The converter calls `ToUniversalTime()` on them, and .NET treats Unspecified as local time. EF applies the converter to query parameters too. So on the store PC (UTC−4), "day starts 04:00Z" becomes 08:00Z: a Z report loses the first 4 hours of the day and takes in 4 hours of the next day. CI runs in UTC, where the shift is zero, so no test catches it. The unit test passes because `DateTime` equality ignores Kind. Any `DateTime` sent by a client without `Z` hits the same bug.
   - **Fix:** In the converter, write `v.Kind == DateTimeKind.Local ? v.ToUniversalTime() : DateTime.SpecifyKind(v, DateTimeKind.Utc)`. In `RangoUtc`, wrap both values in `DateTime.SpecifyKind(..., DateTimeKind.Utc)`. Assert `Kind == Utc` in the test. Add `TZ: America/Santo_Domingo` to the CI job's `env` so time-zone bugs show up in CI.
   - **If we skip it:** Daily sales, Z reports and 606/607 show the wrong totals, but only on real store machines.

## Should fix

3. **A commit can be cancelled by the client, and a failed commit leaves the unit of work broken** (`Persistence/UnitOfWork.cs:L36-43`, `Messaging/Decorators.cs:L67-75`)
   - **What this is:** `EndAsync` commits or rolls back the request's single transaction.
   - **Problem:** `CommitAsync(ct)` uses the request-abort token. If the register's Wi-Fi drops after `SaveChanges`, the commit throws. The client may never learn whether it committed, because cancelling during a SQL Server commit is ambiguous. When the commit throws, `Transaction` is never set back to null. Any later command in the same scope (outbox worker, e-CF queue worker) then sees a transaction and "joins" a dead one. The rest of the `finally` block (detach and clear the trackers) is also skipped.
   - **Fix:** Commit with `CancellationToken.None`, and put the dispose and `Transaction = null` lines in a `try/finally` inside `EndAsync`.
   - **If we skip it:** Once the background workers exist, one failed commit makes every later command in that worker run without a real transaction.

4. **The transaction decorator, the core guarantee of M0, has no test** (`Messaging/Decorators.cs:L42-77`, `Persistence/OutboxYAuditoria.cs:L22-34`)
   - **What this is:** TK-003 and TK-004 promise that a command writes every module, the outbox and the audit log atomically, or writes nothing.
   - **Problem:** No test makes a command fail after it has written something. Nothing checks that the rows, the `ExecuteUpdate` changes and the audit head all roll back. Nothing calls `IOutbox` at all. If someone breaks the rollback (for example by moving `commit = true` up, or by saving one context early), every test still passes.
   - **Fix:** Add one integration test with a test-only command in the test assembly. It adds a user, writes an outbox message, writes an audit record, does one `ExecuteUpdate`, and then returns an error. Assert that none of those rows exist and that `AuditoriaCabeza.Secuencia` did not move. Add a second case where the handler throws. Run it on both databases.
   - **If we skip it:** Half-saved sales (stock taken out, no sale recorded) become possible after any refactor, and nobody notices until the cash count is off.

5. **The supervisor authorization is never used in any test, and its use is not audited** (`Messaging/Decorators.cs:L79-94`, `IdentidadModule.cs:L72-84`)
   - **What this is:** TK-014 is marked done. The decorator consumes a one-time authorization tied to the permission, the resource and the device.
   - **Problem:** No command implements `IRequiereAutorizacion`, so `ConsumirAsync` and the decorator have never run. Single use, expiry, wrong resource and wrong device are all untested. `Un_supervisor_autoriza_con_su_pin` only checks that an id came back. Architecture §8.2 step 4 says the decorator must record who asked and who approved. Today that happens only if each handler remembers to call `IAuditoria`. Also, an endpoint that uses `.RequirePermiso(...)` returns 403 before the decorator runs, so the supervisor path can never be reached there.
   - **Fix:** In the decorator, after a successful consume, write one audit record: `"autorizacion.usada"`, with the permission, the resource and `SupervisorId`. Add a test-only command that implements `IRequiereAutorizacion`, and test that it succeeds once, that a second use gets 403 `Identidad.AutorizacionInvalida`, that another resource or device is refused, and that it expires after 2 minutes. Add a line to the `IRequiereAutorizacion` doc comment: use `.RequireAuthorization()`, not `.RequirePermiso`, on these endpoints.
   - **If we skip it:** The first real user of this path is "void a sale" (TK-045), and its anti-theft check ships untested.

6. **A failed nested command can still have its writes saved** (`Messaging/Decorators.cs:L48`)
   - **What this is:** If a transaction is already open, a command run inside another command simply "joins" it.
   - **Problem:** If the inner command returns an error, nothing undoes what it already added to the change tracker, or what its `ExecuteUpdate` calls changed. If the outer handler handles the error and carries on, the outer commit saves the inner command's half-done work. The inner command's `SupervisorId` also leaks into the outer command's audit record. No code nests commands today. ADR-0001 says modules call each other through `Contracts` interfaces, not commands.
   - **Fix:** Replace the line with `throw new InvalidOperationException("Commands cannot be nested; call the module's Contracts interface.");`. That removes a feature nobody uses.
   - **If we skip it:** The first developer who nests a command gets silent partial writes.

7. **The one-time pairing code and the install step can each be used twice on SQL Server** (`Features/Dispositivos.cs:L65-68`, `Features/Instalar.cs:L38`)
   - **What this is:** A pairing code works once, for 10 minutes. Install works only while there are no users.
   - **Problem:** Both read first and write later. On SQL Server, two requests at the same moment both find the code unused, or both find no users. The result is two devices paired from one code, or two administrators. SQLite serializes them, so the tests pass.
   - **Fix:** For pairing, claim the code the same way `ConsumirAsync` does: `ExecuteUpdateAsync(...UsadoUtc = ahora)` with the same `WHERE`, then continue only if one row changed. For install, a unique-violation catch is enough, or the same claim pattern on the audit head row.
   - **If we skip it:** Someone who sees a pairing code over a shoulder can pair a rogue device at the same moment as the real register.

8. **Any endpoint that forgets `.RequirePermiso` is open to everyone on the LAN** (`Hosts/Abastalia.Host.Local/Program.cs:L28-34`, `IdentidadModule.cs:L27`)
   - **What this is:** Authorization is set per endpoint.
   - **Problem:** There is no fallback policy, so an endpoint without an authorization call is anonymous. M2 will add about 20 endpoints. One missed line exposes, say, price changes without a login.
   - **Fix:** `services.AddAuthorizationBuilder().SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());`. The four public endpoints already say `.AllowAnonymous()`. Add `.AllowAnonymous()` to `/health`, `/openapi` and `/scalar`, or drop the last two in production (see 17).
   - **If we skip it:** One forgotten line becomes a security hole, and no test catches it.

9. **The production host listens only on `http://localhost:5000`, in plain text** (`Hosts/Abastalia.Host.Local/appsettings.json`, `Program.cs`)
   - **What this is:** The API that the registers connect to.
   - **Problem:** No Kestrel endpoint is configured, so the Windows service binds to localhost and the registers cannot reach it. Once someone opens it to the network, the device secret and the session token travel in clear text over the shop Wi-Fi. Anyone who captures them can act as that register and that cashier. ADR-0003 delays only the client certificate (TK-091), not TLS.
   - **Fix:** Add a `Kestrel:Endpoints` HTTPS entry to `appsettings.json` with the node's certificate. Add a line to TK-091/TK-093 saying there is no pilot without HTTPS.
   - **If we skip it:** The pilot install fails on day one, or it works over HTTP and leaks credentials.

10. **The Identidad rules that matter most have no test, and there is no e2e suite yet** (`tests/Abastalia.IntegrationTests/Identidad/IdentidadTests.cs`, `tests/Abastalia.UnitTests`)
    - **What this is:** There are unit tests (lockout, PIN format, money, business day, hash), 10 HTTP integration tests, and 6 architecture tests. They are meaningful: the lockout test even checks the audit chain after a real database round trip. There is no e2e suite (TK-095).
    - **Problem:** Some promised behavior has no test that fails when it breaks:
      - a session stops working after 12 hours
      - a deactivated user loses their open session at once
      - `DELETE /sesiones/actual` ends the session
      - `CambiarMiPin` checks the current PIN
      - an admin cannot deactivate themselves
      - a role change takes effect on the next request
      - two commands that write audit records at the same time keep the chain intact on SQL Server

      `Microsoft.Extensions.TimeProvider.Testing` is referenced but never used.
    - **Fix:** Add one integration test per item above. For expiry, register a `FakeTimeProvider` in `AbastaliaApp` with `ConfigureTestServices` and advance it 12 hours. For the audit chain, fire about 10 parallel failed logins and assert that `VerificarAuditoriaAsync()` is null and that `Secuencia` runs 1..n with no gaps. The e2e suite (TK-095) must start the real host process on a real port against SQL Server and cover:
      - install, then pair 3 registers
      - log in on all 3 at once
      - lockout under parallel attempts
      - a supervisor authorization used by a real command, then refused on reuse
      - revoke a register in the middle of a shift (its next call gets 401)
      - deactivate a user
      - restart the process (data stays, `CrearAlIniciar` skips)
      - check the audit chain at the end

      As later milestones land, extend it to a full store day: sell, void, return, close the shift.
    - **If we skip it:** These rules can break silently. They are exactly what an auditor or a dishonest employee will test.

## Nice to have

11. **An audit write outside a transaction breaks the chain for good** (`Persistence/OutboxYAuditoria.cs:L38-64`)
    - **What this is:** `RegistrarAsync` moves the head row forward with `ExecuteUpdate` and only *adds* the record to the change tracker.
    - **Problem:** If something calls it outside a command (a worker, a query endpoint), the head update commits by itself and the record is never saved. From then on, `VerificarAsync` reports the chain as broken.
    - **Fix:** Inject `UnitOfWork` and throw if `Transaction` is null. One line.
    - **If we skip it:** The nightly check (TK-094) reports false tampering after the first misuse.

12. **Unique-index clashes return 500, and user codes behave differently on the two databases** (`Features/Usuarios.cs:L36`, `Messaging/Decorators.cs:L63`)
    - **What this is:** `Usuarios.Codigo` has a unique index.
    - **Problem:** Two admins creating the same code at once get a `DbUpdateException`, which becomes a 500. SQL Server's default collation ignores case and SQLite does not. So "Ana" and "ana" are two users in dev, but a conflict in production, and login with "ana" works only on SQL Server.
    - **Fix:** In the decorator, catch `DbUpdateException` when the inner exception is a unique violation and return `Error.Conflict`. Store codes trimmed and upper-cased (`ToUpperInvariant()`), and compare them that way.
    - **If we skip it:** You get a rare 500 and some login confusion that only happens in production.

13. **Missing validators turn bad input into 500s** (`Features/Dispositivos.cs:L54-75`, `Features/Sesiones.cs:L123-126`)
    - **Problem:** `POST /dispositivos/emparejar` with `{}` hits `c.Codigo.Trim()` on null, and this endpoint is anonymous. `CambiarMiPin` with no `PinActual` makes `PasswordHasher` throw.
    - **Fix:** Add a `Validator` with `NotEmpty()` on those fields.
    - **If we skip it:** Noisy 500s in the logs instead of 400s.

14. **Changing a PIN does not end the user's other sessions** (`Features/Sesiones.cs:L128-137`, `Features/Usuarios.cs:L82`)
    - **Problem:** A cashier who suspects a coworker used their session on register 2 changes their PIN, but that session stays valid for up to 12 hours.
    - **Fix:** On a PIN change, close the user's other open sessions with the same `ExecuteUpdate` used for deactivation (keep the current session in `CambiarMiPin`).
    - **If we skip it:** Changing the PIN does not do what the user expects.

15. **The Administrador role's permissions are stored data, so new permissions never reach it** (`Domain/Identidad.cs:L23`, `Persistence/IdentidadDbContext.cs:L40`)
    - **Problem:** `HasData` runs only when the database is created. When M3 adds a new constant to `Permisos.Todos`, the admin in an existing database lacks it and gets 403. It also lets anyone with `usuarios.gestionar` add any permission to their own role or create an admin user, so that permission is admin-equivalent.
    - **Fix:** In the authentication handler, grant `Permisos.Todos` when `RolId == Rol.AdministradorId`. Only an administrator may assign the Administrador role or edit the role they hold.
    - **If we skip it:** The owner is locked out of new features after each upgrade, until migrations (TK-090) patch the data.

16. **`IntegrationEvent.OcurridoUtc` uses `DateTime.UtcNow`** (`Abastalia.SharedKernel/IntegrationEvent.cs:L15`)
    - **Problem:** It breaks the "clock always through TimeProvider" rule, so tests cannot control event times.
    - **Fix:** Let the outbox set `OcurridoUtc` from `TimeProvider` when the event has none, or pass the time in.

17. **The API docs are published in production** (`Hosts/Abastalia.Host.Local/Program.cs:L31-32`)
    - **Fix:** Map OpenAPI and Scalar only when `app.Environment.IsDevelopment()`.

18. **Lean: unused code and packages**
    - `IQuery`, `IQueryHandler`, `ValidacionQueryDecorator` and their scan and decorate lines have no implementations, because queries live in endpoints (`Messaging/Handlers.cs:L13-19`, `Decorators.cs:L20-26`, `AbastaliaServices.cs:L33,L39`). Delete them until a query needs validation.
    - `Result.Success()`, `Result.Failure()`, `Result.Success<T>()` and the non-generic implicit operator are unused (`Result.cs:L25-29`).
    - `NSubstitute` (unit tests), `ClosedXML` and `Microsoft.EntityFrameworkCore.Design` are listed but nothing uses them.
    - The SQL Server test image uses the floating tag `2025-latest` (`AbastaliaApp.cs:L24`). Pin a dated tag so CI does not change under you.

Verdict: fix 1 and 2 first. Then do 3 to 5 before M2 code starts using the pipeline, and 9 before the pilot.
