# R2 · Review of M2 (commit d41b831, as of af922e8)

Scope: `src/Modules/Settings/**`, `src/Modules/Inventory/**`, `src/BuildingBlocks/Abastalia.SharedKernel/Itbis.cs`, and their tests (`tests/Abastalia.UnitTests/Inventario`, `tests/Abastalia.IntegrationTests/Inventario`, `tests/Abastalia.IntegrationTests/Infra/Catalogo.cs`). I read the building blocks they depend on (decorators, unit of work, audit, permissions) to follow the real flow.
Load assumed: one store, the main PC as the server on SQL Server Express, about 3 registers selling the same popular products (chuleta, pollo, queso) at the same time, plus one or two back-office users doing counts, adjustments and transfers during opening hours. Local tests run on SQLite. SQLite runs each write transaction alone (`BEGIN IMMEDIATE`), so races and deadlocks never show up locally.
State checked: `dotnet build Abastalia.slnx` is clean (0 warnings, 0 errors). `dotnet test` passes 70 of 70 tests on SQLite (unit, integration, architecture). The SQL Server suite was not run here (no Docker).

What this change does: It adds the shop settings (name, RNC, receipt footer, discount cap) and the inventory module. The inventory module has categories with notes, products by unit or by pound, presentations, barcodes, PLU and EAN-13 scale labels. It also adds a stock ledger ("kardex": movement rows that are never changed) with current stock per warehouse, weighted average cost, adjustments with a reason, transfers, and blind physical counts. Other modules (sales and purchases, M4 and M6) will move stock through the `IMovimientosInventario` interface inside their own transaction.

## Must fix

1. **Applying a count erases every sale made while the count was open** (`InventarioModule.cs:L113-121`, `Features/Conteos.cs:L110-138`)
   - **What this is:** `AplicarConteo` calls `FijarAsync` for each counted line. `FijarAsync` reads the stock, then sets it to the counted number (an absolute value), and writes a kardex row for "counted minus what I read".
   - **Problem:** A store does not close while it counts. Say the counter counts 10 lb of chuleta at 9:00, the registers sell 3 lb at 9:30, and the supervisor applies the count at 10:00. Stock becomes 10, but the shelf has 7. The 3 lb sale is gone from stock, so the store "finds" 3 lb that do not exist. There is a second, smaller race inside `FijarAsync` on SQL Server: a sale can commit between the read on L116 and the update on L117. Then the kardex rows no longer add up to the stock, which breaks the core promise of TK-060. Also, nothing stops two applies of the same count at the same time. The count row has no concurrency token, so both see `Abierto` and both run.
   - **Fix:** Take the snapshot when the line is counted, not when the count is applied. In `RegistrarConteo`, save the current system stock in a hidden field for that line, for example `ConteoLinea.SistemaAlContar`. Never return it from any endpoint. In `AplicarConteo`, first claim the count: `ExecuteUpdateAsync(Estado = Aplicado)` with `WHERE Id = @id AND Estado = 'Abierto'`, and stop with `ConteoErrors.NoAbierto` if 0 rows changed. Then apply `delta = Contado - SistemaAlContar` as a relative update, `Cantidad = Cantidad + delta`, which is atomic like the sale decrement. Read the resulting stock afterwards, and write that delta to the kardex. `FijarAsync` becomes a relative "apply delta" method. Add an integration test: start a count, register 10, sell or adjust -3, apply, and expect 7.
   - **If we skip it:** Every count done during opening hours puts wrong stock into the system. That is pain #1 in `funcionalidades-v1.md` ("the numbers don't add up"), and the count is the tool that is supposed to fix it.

2. **The blind count is not blind: any logged-in user can see the system stock by scanning the product** (`Features/CodigosYPresentaciones.cs:L154,L160-162`, `Features/Productos.cs:L206-208,L221`)
   - **What this is:** Counters work with `inventario.contar`. `GET /conteos/{id}` correctly hides the expected quantity.
   - **Problem:** `GET /productos/por-codigo/{codigo}` and `GET /productos?buscar=` only need a login. Both return `Existencia`. A counter with only `inventario.contar`, the exact role in the test, scans the jamón and sees "10". They can then type 10 and hide the 0.5 lb that went missing. The test only checks that the count endpoint has no "sistema" field, so it does not catch this.
   - **Fix:** In both endpoints, inject `IUserContext` and return `Existencia` only when `usuario.Tiene(Permisos.InventarioVer)`. Otherwise return null (make the field `decimal?`). Extend the blind-count test: the counter calls `por-codigo` and the search, and `existencia` is null.
   - **If we skip it:** The anti-theft control in TK-062 does nothing against the person it is meant to check.

3. **Stock updates and the audit head lock rows in different orders, so SQL Server will deadlock under normal register traffic** (`InventarioModule.cs:L64,L89,L145-146`, `BuildingBlocks/Messaging/Decorators.cs:L94`)
   - **What this is:** On SQL Server, the decrement `UPDATE ... WHERE Cantidad >= q` takes an exclusive lock on the stock row and holds it until commit. That part is correct: two registers cannot both sell the last pound. The audit head row (`CabezaAuditoria`) is one row that every audited command locks until commit.
   - **Problem:** A deadlock is when two transactions each hold a lock the other one needs, so SQL Server kills one of them. There are two ways this happens here:
     - `Agrupar` keeps the order the cashier scanned in. Register 1 sells [chuleta, pollo] while register 2 sells [pollo, chuleta]. Each one locks its first row and then waits for the other's row.
     - `AutorizacionDecorator` writes `autorizacion.usada`, which locks the audit head *before* the handler runs. Every handler that changes stock writes its audit record *after* the stock rows. So a supervisor-approved count apply (and, in M4, a supervisor-approved void) holds the head and waits for a stock row. At the same time, an adjustment or sale holds that stock row and waits for the head.

     The loser gets `SqlException 1205`. `ExecuteUpdateAsync` throws it directly, not as a `DbUpdateException`, so the transaction decorator does not catch it and the register sees a 500. SQLite never shows this.
   - **Fix:** Sort the lines by `ProductoId` before you touch any row. In `Agrupar`, add `.OrderBy(g => g.Key)`, and do the same in `RegistrarEntradaAsync` (returns and voids come in through it). In `AutorizacionDecorator`, write the `autorizacion.usada` record after `inner.Handle` succeeds, so the audit head is always the last lock a command takes. Add a CI-only (SQL Server) test that runs about 20 parallel two-line adjustments in opposite orders and expects no 500. Transfers in opposite directions at the same moment can still deadlock. That is rare back-office work and is acceptable.
   - **If we skip it:** Once M4 ships, a register sometimes fails a sale with a 500 at the busiest moment, the cashier scans everything again, and nobody can reproduce it on a dev machine.

## Should fix

4. **Products that may be sold without stock can also be adjusted and transferred out of stock that does not exist** (`InventarioModule.cs:L71`, `Features/Ajustes.cs:L19,L43-45,L84-86`)
   - **What this is:** `VenderSinExistencia` lets a sale take stock below zero and flags the shelf for counting. `AjustarInventario`'s doc comment says "Removing more than there is fails: count first."
   - **Problem:** Adjustments and transfers use the same `RegistrarSalidaAsync`, so the sales flag applies to them too. For pollo with `VenderSinExistencia = true` and 0 lb in Tienda, a transfer of 50 lb from Tienda to Cuarto frío (an easy direction mistake) succeeds. Tienda shows -50 and the cold room shows +50 of chicken it never received. A merma (shrink) of -100 succeeds the same way.
   - **Fix:** Add a `bool permitirNegativo` parameter to the internal method. Only the sale path (the `IMovimientosInventario` contract) passes `producto.VenderSinExistencia`. Adjustments and transfers pass `false`. Add one test.
   - **If we skip it:** Stock per warehouse is wrong whenever someone makes a typo, and nothing stops it.

5. **PLUs with leading zeros match in some cases and not in others** (`Features/CodigosYPresentaciones.cs:L138-147`, `Features/Productos.cs:L22,L71,L124`)
   - **What this is:** A scale label carries a 4- or 5-digit PLU. The lookup tries the PLU as printed and with the leading zeros removed.
   - **Problem:** The product's PLU is stored exactly as typed, and "321", "0321" and "00321" are three different values to the unique index. A product saved as "0321" is never found from a 5-digit label ("00321" or "321"), so the cashier gets a 404. If two products are saved as "321" and "00321" (allowed today), the label query matches both and `FirstOrDefault` with no `ORDER BY` returns either one, which can be the wrong product at the wrong price. A PLU typed by hand at the register ("0321") is not trimmed at all.
   - **Fix:** Store the PLU without leading zeros: `Plu = c.Plu?.TrimStart('0')`. Reject an empty result in the validator. Look it up only by the trimmed value, for both labels and typed codes. Then the unique index really means "one product per PLU". Add a test with PLU "321" and both a 4-digit and a 5-digit label format.
   - **If we skip it:** Weighed products sometimes do not scan, or they ring up as another product.

6. **A count line for an unknown product makes the count impossible to apply** (`Features/Conteos.cs:L75-80,L125-129`)
   - **Problem:** `RegistrarConteo` accepts any `ProductoId`. One wrong id (a stale tablet list, or a deleted product) makes `AplicarConteo` crash with a 500. `FijarAsync` inserts a stock row for the unknown product, then `SingleAsync` on its cost throws, or `productos[l.ProductoId]` throws. There is no cancel endpoint (`EstadoConteo.Cancelado` is never set), and the bad line cannot be removed, so the whole count is stuck.
   - **Fix:** In `RegistrarConteo`, check that every `ProductoId` is an existing product. Return 404 `ProductoNoEncontrado` otherwise.
   - **If we skip it:** A 300-line count done over an hour has to be thrown away and done again.

7. **The adjustment reason never reaches the kardex** (`Features/Ajustes.cs:L42-45`, `InventarioModule.cs:L81,L107`)
   - **What this is:** TK-061 is "adjustments with a reason (merma, damage, consumption, correction)". The kardex has a `Motivo` column, and the kardex endpoint returns it.
   - **Problem:** `RegistrarEntradaAsync` and `RegistrarSalidaAsync` always pass `motivo: null`. For an adjustment, the kardex says `Ajuste` with no reason. The reason and the note only exist inside the audit JSON. A "shrink by reason" report (shrink is the butcher's main loss) cannot be built from the ledger.
   - **Fix:** Add an optional `string? motivo` to both internal methods and pass `$"{c.Motivo}: {c.Nota}"` from `AjustarInventario`. Either limit `Nota` to 180 characters or give `Movimiento.Motivo` `HasMaxLength(250)`. Otherwise reason plus note can go over the default 200 and fail on SQL Server only (see 9). Assert the reason in the existing adjustment test.
   - **If we skip it:** Shrink reports have to read the audit log, or cannot be made.

8. **Quantities and prices accept any number of decimals, and SQL Server and SQLite store them differently** (`Features/Productos.cs:L17-29,L60-61`, `Features/Ajustes.cs:L29,L73`, `Features/Conteos.cs:L65`, `Features/CodigosYPresentaciones.cs:L71-73`)
   - **What this is:** Every decimal column is `decimal(19,4)`. `funcionalidades-v1.md` says quantities have 3 decimals.
   - **Problem:** An adjustment of `-1.23456` lb is stored as `1.2345` or `1.2346` on SQL Server (EF sends a scale-4 parameter). SQLite stores the full text `1.23456`. The kardex result and later comparisons then differ between dev and production. Products sold by unit also accept fractions: "-0.5 bottles of Presidente" is a valid adjustment, transfer or count.
   - **Fix:** Add FluentValidation `PrecisionScale(19, 3, true)` to every quantity (adjustment, transfer line, counted quantity, opening stock, minimum stock, presentation factor). Add `PrecisionScale(19, 2, true)` to prices and `PrecisionScale(19, 4, true)` to cost. In the movement methods, return a validation error when the product's `Unidad == Unidad` and the quantity is not a whole number.
   - **If we skip it:** Small differences show up only in production, and unit products can end up with fractional stock.

9. **Text lengths are only enforced on SQL Server, so some inputs give a 500 only in production** (`ConfiguracionModule.cs:L78-88`, `Persistence/InventarioDbContext.cs:L48-51`, `Features/Categorias.cs:L28`)
   - **Problem:** SQLite ignores `nvarchar(n)`. On SQL Server, a `Direccion` or `Telefono` longer than 200 characters (the convention's default, and these fields have no validator) fails with "String or binary data would be truncated", which becomes a 500. The same happens to a category with more than about 33 notes of 60 characters (the `Notas` column is 2000 characters, and the number of notes has no limit). A note that contains a line break is silently split in two, because the converter joins the notes with `'\n'`.
   - **Fix:** `RuleFor(c => c.Direccion).MaximumLength(200)` and the same for `Telefono` (and limit `Rnc` to 11). For `Notas`, add `RuleFor(c => c.Notas).Must(n => n is null || n.Count <= 20)`, and add `.Must(n => !n.Contains('\n'))` to each note.
   - **If we skip it:** The owner hits a 500 while filling in the shop settings on the pilot machine. Nobody sees it in dev.

10. **The price permission can be bypassed, and some catalog changes have no audit record** (`Features/Productos.cs:L66-90,L124,L134`, `Features/CodigosYPresentaciones.cs:L50-55,L95`)
    - **What this is:** `precios.cambiar` is meant to separate "keeps the catalog" from "sets prices".
    - **Problem:** A user with only `productos.gestionar` can:
      - create "Chuleta" at RD$ 1 (`CrearProducto` sets a price without checking the permission)
      - move the real chuleta's PLU or barcode to that product (`ActualizarProducto` changes `Plu` freely, and `DELETE .../codigos/{codigo}` plus `POST .../codigos` move barcodes)

      Every scale label and scan then sells at RD$ 1. Two of these changes also leave no trace. Barcode delete is a bare `ExecuteDeleteAsync` in the endpoint: it runs outside the command pipeline, with no transaction, no audit and no outbox. Presentation price changes are audited without the old price, and no `PrecioCambiadoV1` event is sent.
    - **Fix:** In `CrearProducto`, require `precios.cambiar` (or force the price through the same check as an edit). Make barcode delete a command with an audit record, like `AgregarCodigo`. In `GuardarPresentacion`, audit `{ antes, despues }` and send `PrecioCambiadoV1` when the price changes.
    - **If we skip it:** The permission split looks safe on the role screen but does not protect the prices.

11. **The riskiest inventory paths have no test that fails when they break** (`tests/Abastalia.IntegrationTests/Inventario/InventarioTests.cs`, `tests/Abastalia.UnitTests/Inventario/InventarioTests.cs`)
    - **What this is:** There are 8 good HTTP tests: scanning, labels, duplicate codes, adjustment limit plus kardex, price permission plus version, transfer, and the blind count with a supervisor and single use. There are 7 unit tests for the label parser and the average formula. They assert real values and check the audit chain.
    - **Problem:** These promised behaviors have no test:
      - **Weighted average cost through the database:** `RegistrarEntradaAsync(actualizarCosto: true)` has never run. Its `SumAsync` over a decimal column (special handling on SQLite) and the cost update are dead until M6. TK-060 is marked done.
      - **Two registers selling the last pound at once:** only one succeeds, and stock is never below zero.
      - **`VenderSinExistencia`:** a sale goes negative and sets `PendienteContar`. A count clears the flag.
      - **The kardex rule:** the sum of a product's movements equals its stock, and the last `ExistenciaResultante` equals its stock.
      - **Price labels (prefix 22) end to end:** a presentation barcode returns the presentation price and factor. The wholesale price level (TK-024) is never read.
      - **Configuración (TK-020):** no test updates the shop data, checks the permission, rejects a bad RNC, or checks the audit record. The backlog rule says no ticket closes without an integration test of its main path.
      - **`Itbis.Incluido`:** no unit test (for example 118.00 at 18% gives 18.00, 116.00 at 16% gives 16.00, 0 for exempt). M4 will build the totals engine on it.
      - **Formats:** `PUT /formatos-etiqueta` and a label in a custom format.
    - **Fix:** Add one integration test per item. Use `ComandosDePrueba` to call `IMovimientosInventario` directly for the sale and purchase paths until M4 and M6 exist. Run the parallel ones on both databases; they only prove something on SQL Server. The e2e suite (TK-095) must start the real process on SQL Server and, for inventory, cover:
      - 3 registers selling the same weighed product at the same time until it runs out, with exactly the right number of sales passing
      - multi-line sales in opposite scan orders (no 500)
      - weight and price labels with leading-zero PLUs
      - a blind count while the registers keep selling, applied with a supervisor, with stock equal to counted minus the sales after the count
      - a purchase changing the average cost, and the next sale's kardex cost
      - void and return putting stock back
      - a transfer, then a sale from the destination
      - a process restart (stock and kardex survive)
      - at the end, for every product and warehouse, the sum of the kardex equals the stock, and the audit chain verifies
    - **If we skip it:** Items 1, 3 and 4 above went unnoticed for this reason, and the next ones will too.

12. **Applying a big count freezes the registers for seconds** (`InventarioModule.cs:L113-121`, `Features/Conteos.cs:L122-132`)
    - **Problem:** Each counted line costs 4 database round trips (an exists check, a read, an update and a cost read), all inside one transaction. Each stock row stays locked until the end. A full count of a minimarket (about 3,000 lines) means about 12,000 queries. Sales of any product already processed wait until the whole apply commits.
    - **Fix:** When you rewrite this for finding 1, load the costs and stock rows once with the existing `productos` and `sistema` dictionaries, and apply each delta with a single `ExecuteUpdate` per line. That is 1 query per line instead of 4. Sort by `ProductoId` (see 3).
    - **If we skip it:** The supervisor presses "apply" and all 3 registers hang until it finishes.

## Nice to have

13. **`AsegurarExistenciaAsync` is a check-then-insert that saves early, and it can go away** (`InventarioModule.cs:L135-140`)
    - **Problem:** Two transactions that are the first to move a product into a new warehouse both see "no row" and both insert. On SQL Server the second gets a key violation and returns the generic 409 "Duplicado". It also calls `SaveChangesAsync` in the middle of another module's command, which flushes everything pending in that context.
    - **Fix:** Create the stock rows up front: one per warehouse when a product is created, and one per product when a warehouse is created. Then delete `AsegurarExistenciaAsync` and its 3 calls. A missing row makes the conditional update return 0, which already means "no stock".

14. **Search ignores accents differently on each database** (`Persistence/InventarioDbContext.cs:L56`)
    - **Problem:** On SQL Server's default collation, a cashier who types "jamon" does not find "Jamón". On SQLite, case-insensitive search only works for ASCII.
    - **Fix:** On SQL Server only, `b.Property(p => p.Nombre).UseCollation("Latin1_General_100_CI_AI")`, set when the provider is SQL Server.

15. **Two purchases of the same product at the same moment can lose one cost update** (`InventarioModule.cs:L96-101`)
    - **Problem:** The total stock and the current cost are read without a lock, so the last writer wins. Purchases are back-office work, so this is rare.
    - **Fix:** Update the stock row before you read the total, which takes the lock first. Or lock the product row first: `ExecuteUpdate` with `Version = Version` is enough to take the lock.

16. **A scan returns lines that the sale will refuse later** (`Features/CodigosYPresentaciones.cs:L156-162`)
    - **Problem:** A barcode that points to an inactive presentation is returned as sellable. A weight label for a product sold by unit returns a pound quantity. The sale (M4) rejects both, after the cashier has already moved on.
    - **Fix:** Return 409 for an inactive presentation, and 400 for a weight label on a product whose `Unidad` is not `Libra`.

    - With 13 done, `AsegurarExistenciaAsync` and its calls go away (about 8 lines).
