## Must fix

1. **The nightly backup never runs on a PC that is off at night** (`Configuracion/Respaldos.cs:L117-138`)
   - **What this is:** `RespaldoNocturno` waits until 23:30 store time and then backs up. Nothing else triggers a backup.
   - **Problem:** It is the same pattern R5 #5 fixed for the audit check. Many colmados and butcher shops switch the PC off at closing, often before 23:30. The service then starts in the morning, waits for a 23:30 it never reaches, and is stopped again at night. Those stores never get a single backup. The `respaldo` health check turns Degraded after 36 hours, but nobody watches `/health` yet, and the owner believes backups run because the README says so.
   - **Fix:** Back up a few minutes after start when the newest backup is older than 20 hours, then every day at 23:30. That is one check before the loop, the same shape as `VerificacionNocturnaAuditoria`. Move the body into a public method, as was done for `VerificarAsync`, so a test can call it. Test: with the phrase set and no backup in the folder, calling that method makes one backup. Calling it again right away makes none.
   - **If we skip it:** The stores most likely to lose their PC (cheap hardware, switched off at the wall) are the ones with no backups.

2. **On SQL Server, backups fail under the service account and leave an unencrypted copy of the database every night** (`Respaldos.cs:L22-23`, `L42-44`, `L50`, `L55`, `L67-70`, `RespaldosTests.cs:L39`)
   - **What this is:** SQL Server writes the plain `.bak` to its own default folder (`InstanceDefaultBackupPath`, for example `C:\Program Files\Microsoft SQL Server\MSSQL16.SQLEXPRESS\MSSQL\Backup`). Abastalia then opens that file, encrypts it into `C:\ProgramData\Abastalia\respaldos` and deletes it in `finally`.
   - **Problem:** On a default SQL Server Express install, that folder is open only to Administrators, SYSTEM and SQL Server's own service account. The installer runs Abastalia as `NT SERVICE\Abastalia`, with no admin rights. So `BACKUP DATABASE` succeeds (the login owns the database), `File.OpenRead` at L55 fails with "access denied", and `File.Delete` in `finally` fails the same way. That second error hides the first. Each night a new full, unencrypted `.bak` stays behind (the names carry the time, so none is overwritten), and no encrypted backup is made. Even running as LocalSystem, a power cut or crash between L50 and L69 leaves a plain `.bak` there forever, because nothing cleans that folder. The only test of this path is skipped on SQL Server, so it has never run.
   - **Fix:** Have SQL Server write the `.bak` into a Abastalia work folder, `C:\ProgramData\Abastalia\respaldos\trabajo`. In `preparar-servicio`, give SQL Server's service account (`NT SERVICE\MSSQL$SQLEXPRESS`, or the account read from the instance) Modify on that folder. Abastalia already has Modify on `C:\ProgramData\Abastalia`, and inheritance lets it read and delete what SQL Server writes there. At the start of `CrearAsync`, delete any `*.bak` or `*.tmp` left in the work folder. A container test cannot cover Windows folder permissions, so check it once on the clean Windows VM with the installer (R5 #6 needs that VM too): one backup, then `descifrar-respaldo`, then `RESTORE VERIFYONLY` on the result.
   - **If we skip it:** The first pilot store has no backups, plus a growing pile of plain copies of its database (customers, RNCs, PIN hashes) that fills the disk.

## Should fix

3. **A cut backup file counts as the newest backup** (`Respaldos.cs:L54-57`, `L64`, `L74-75`, `L107`, `L146-149`)
   - **Problem:** The encrypted file is created under its final name and filled chunk by chunk. If the run stops halfway, the partial file stays. A run can stop halfway because the owner shuts the PC down during the 23:30 run (the stopping token), because the back-office gives up on `POST /api/respaldos` after its 100-second HTTP timeout (the backup runs on the request's token, and a few-GB database takes longer), or because the disk fills. `Listar()` then shows the cut file as the newest backup, the health check says Healthy, and retention deletes the oldest good backup to make room for it. Nobody finds out until a restore fails with "El respaldo está cortado".
   - **Fix:** Write to `destino + ".parcial"` and `File.Move` it to the final name only after `CifrarAsync` returns. On any error, delete the partial file. Run the manual backup with the host's stopping token, not the request's, so a dropped client does not cut it. Test: cancel the token during `CrearAsync` and check that no `*.abastalia-respaldo` file is left.
   - **If we skip it:** The newest backup can be the one that does not restore.

4. **`BACKUP DATABASE` runs with a 30-second limit** (`Respaldos.cs:L50`)
   - **Problem:** Nothing sets a command timeout, so EF uses SqlClient's default of 30 seconds. `BACKUP` reads and writes the whole database. A few-GB database on a store PC with a hard disk can take longer than that. SQL Server then aborts the backup, and every night fails the same way from then on.
   - **Fix:** One line before L50: `db.Database.SetCommandTimeout(TimeSpan.FromHours(1));`. The context is scoped, so this changes nothing else.
   - **If we skip it:** Backups stop on their own once the database grows past what the disk can copy in 30 seconds, typically some months after go-live.

5. **If the Data Protection keys are lost, backups stop with no clear message** (`ConfiguracionModule.cs:L28`, `Respaldos.cs:L37`, `L141-151`)
   - **What this is:** The key derived from the passphrase is stored in `Negocio.RespaldoClave`, encrypted with ASP.NET Core Data Protection. Its key ring lives in the service account's Windows profile and is protected with that account's DPAPI key.
   - **Problem:** The ring is gone, or unreadable, when the database is restored onto a new PC after the old one died (the exact case backups exist for), when the service is reinstalled under another account or name, or when the profile is reset. `Protector.Unprotect` then throws `CryptographicException` ("key not found"). Every nightly run logs "Falló el respaldo nocturno", `POST /api/respaldos` returns 500, and 36 hours later the health check only says "El último respaldo tiene más de 36 horas." Nothing tells the owner that typing the phrase again fixes it. Old backups are still safe, because they only need the phrase.
   - **Fix:** Catch `CryptographicException` at L37 and return `Error.Conflict("Respaldo.FraseIlegible", "Vuelva a escribir la frase de los respaldos: la clave guardada no se puede leer en esta PC.")`. Have the health check try the same `Unprotect` and report that text. Also keep the ring in a known place the installer already prepares: `.PersistKeysToFileSystem(new DirectoryInfo(@"C:\ProgramData\Abastalia\claves")).ProtectKeysWithDpapi()`. Test: write a garbage `RespaldoClave`, then `POST /api/respaldos` returns 409 `Respaldo.FraseIlegible`, and `/health` is Degraded.
   - **If we skip it:** After a disaster recovery, the store runs with no backups until someone reads the logs.

6. **The off-PC copy is never cleaned, and a failed copy stops the local cleanup** (`Respaldos.cs:L59-64`)
   - **Problem:** Retention (L64) runs only on `Carpeta`, so `Respaldo:CopiaEn` (a USB stick or a network folder) gets one more full backup every night. A 32 GB stick with 300 MB backups is full after about 100 days. From then on, `File.Copy` throws, L64 never runs, and the local folder also grows by one full backup per night until the system disk fills and SQL Server cannot grow the database. An unplugged stick or an offline share has the same effect.
   - **Fix:** Run retention before the copy, on both folders. Put the copy in its own `try`, log a failure, and have the health check say "no se pudo copiar a …". Test: point `CopiaEn` at an existing file (so `CreateDirectory` throws), make 15 backups, and check that the local folder still keeps 14.
   - **If we skip it:** A full USB stick stops the store months later, for a reason nobody connects to backups.

7. **The GCM nonce has only 4 random bytes for a key that never changes, and the header is not authenticated** (`CifradoRespaldo.cs:L23`, `L24-29`, `L41`, `L57-60`, `L79-85`)
   - **What this is:** Every backup of a store uses the same key (derived once from the phrase). The nonce is 4 random bytes plus the chunk number.
   - **Problem:** If two backups draw the same 4 bytes, they reuse every nonce. The odds are about n²/2³³: about 0.2 % for one store that backs up nightly for 10 years, so across 1,000 stores a couple will hit it. A reused GCM nonce leaks the XOR of the two plaintexts and lets anyone holding both files compute the authentication key, so they can forge a backup that decrypts without error. Also, the salt, iteration count and nonce prefix in the header are not authenticated. An edited header with 2,000,000,000 iterations makes `descifrar-respaldo` run for hours, and a negative count throws `ArgumentOutOfRangeException` instead of `CryptographicException`. No backup exists yet, so the format can change for free now.
   - **Fix:** Put 16 random bytes per file in the header. Derive a per-file key with `HKDF.DeriveKey(HashAlgorithmName.SHA256, clave, 32, salt: thoseBytes)`, and use the plain chunk number as the nonce. Pass the 32-byte header plus the last-chunk flag as associated data on every chunk. Reject iteration counts outside 100,000 to 10,000,000. That is about 8 changed lines. Test: change one header byte and expect `CryptographicException`. Encrypt the same data twice and check that the outputs differ.
   - **If we skip it:** It is a rare but real weakness in the one file format that is meant to outlive the PC, and it can only be fixed cheaply before the first backup exists.

8. **The outbox spins at full speed once 100 messages fail** (`Messaging/ProcesadorOutbox.cs:L30`, `L43-46`, `L67-69`)
   - **What this is:** Each pass takes the oldest 100 unprocessed messages. A failed message is logged and stays unprocessed. The worker repeats passes while a pass took 100.
   - **Problem:** A failed message stays first in line. Once 100 messages fail (a bug in a handler for a frequent event; today only `TurnoCerradoV1` has one, but TK-088 will add the cloud upload), every pass takes the same 100, fails them all and returns 100. The `while` never waits, so one CPU core and SQL Server stay busy without pause, 100 errors with stack traces are logged per pass (the 60 × 50 MB log files roll over in hours and lose the first error), and message 101 onward is never delivered. Also, all handlers of a pass share one DI scope. A handler that fails after `Add` leaves the entity tracked, so the next message's `SaveChanges` tries to insert it again and fails too.
   - **Fix:** Read each message once per run: `Where(m => m.ProcesadoUtc == null && m.Secuencia > desde)`, with `desde` set to the last `Secuencia` taken. `ProcesarAsync` returns it, and the worker loops on it. Create a scope per message inside the loop. Test: a handler that always throws, 150 failing events and one good event after them. One run of the worker loop returns, and the good event is processed.
   - **If we skip it:** One handler bug turns into a server pegged at 100 % CPU, with logs that no longer show the cause.

9. **Seeds of rows the owner edits will be overwritten by future migrations** (`Identidad/Domain/Identidad.cs:L24`, `IdentidadDbContext.cs:L45`, `ConfiguracionModule.cs:L67`, `InventarioDbContext.cs:L111`)
   - **What this is:** `HasData` seeds the default roles, the `Negocio` row and the scale label formats. Before migrations, a seed change did nothing to an existing database. Now `migrations add` turns any seed change into `UpdateData`, `InsertData` or `DeleteData` that runs in every store.
   - **Problem:** The Supervisor seed is computed as `Permisos.Todos` minus the admin-only permissions. The owner can edit Supervisor and Cajero (only Administrador is protected). The next time a developer adds a permission, `MigracionesTests` asks for a migration, and that migration rewrites Supervisor's whole list in every store. Example: the owner removed `ventas.anular` from Supervisor. After the update, supervisors can void sales again, and nothing says so. The same applies to `Negocio`: its seed comes from property initializers (`TopeDescuentoPct = 10`), so changing a default overwrites the owner's value. Label formats are replaced wholesale by the owner, so a future `InsertData` of a prefix the owner already created fails the migration, and the service does not start.
   - **Fix:** Write the Supervisor and Cajero seed lists as literals, not derived from `Permisos.Todos`. Then a new permission only changes the Administrador row, which the owner cannot edit and which should get it. Give `Negocio` an explicit seed object instead of the initializers. Add a guard to `MigracionesTests`: no migration after `Inicial*` may contain `UpdateData`, `InsertData` or `DeleteData` on `Roles` (except Administrador), `Negocio` or `FormatosEtiqueta`. Such changes go through `migrationBuilder.Sql` written to respect the owner's data. The guard is about 6 lines over `IMigrationsAssembly.Migrations`.
   - **If we skip it:** An ordinary feature update silently gives back permissions the owner took away.

10. **Startup migrations have a 30-second limit and run before the service tells Windows it started** (`AbastaliaServices.cs:L64-71`, `Program.cs:L89`)
    - **Problem:** `MigrateAsync` uses the context's default 30-second command timeout for each statement. A later migration that builds an index or rewrites a column on `LineasVenta` or `AuditoriaRegistros` with a year of rows can take longer on SQL Server Express. That migration then rolls back, the process exits, and the installer's restart-on-failure tries the same thing forever. The store is down after an update. Separately, the migrations run before `app.RunAsync()`, which is where the process tells the Service Control Manager that it started. Windows allows 30 seconds for that, then reports error 1053 and treats the start as failed.
    - **Fix:** Call `db.Database.SetCommandTimeout(TimeSpan.FromMinutes(30))` before each `MigrateAsync`. Run `CrearBaseDeDatosAsync` from the `StartingAsync` of a small `IHostedLifecycleService` registered first. That runs after the service has reported "started" and before Kestrel listens or any worker starts, so no request sees a half-migrated database. Check it once on the VM with a migration that runs `WAITFOR DELAY '00:00:45'`.
    - **If we skip it:** The first slow migration takes every store down at update time, and the cause is hard to see from the store.

11. **R5 #3 is not fully closed: the 606 codes every cash purchase as paid in cash** (`Compras/Features/GastosYPagos.cs:L296-298`)
    - **Problem:** `FormaPago` is 1 (efectivo) for every `Contado` purchase or expense and 4 for every `Credito` one, and `FechaPago` is always empty. R5 #3 asked for the code from the medium that paid it. Abastalia does not record how a contado purchase or expense was paid (only `PagoSuplidor` has a `Medio`, and only credit purchases get one), so a contado purchase paid by transfer is declared as cash. The accountant has to find those rows and fix them by hand. A wrong payment form on a large purchase may also matter for its deductibility (the accountant should confirm).
    - **Fix:** Add an optional `Medio` to contado purchases and expenses, and map it to 1, 2 or 3. Until then, leave `FormaPago` empty for contado rows instead of guessing. Fill `FechaPago` with the invoice date for contado rows, since Abastalia knows it. Test in `ComprasTests`: a contado expense paid by transfer gives `FormaPago = 2` and `FechaPago` = its date. A credit purchase gives 4 and an empty date.
    - **If we skip it:** The 606 still needs manual fixing each month, which is what TK-054 was meant to remove.

Findings 2, 5 and 10 come from how Windows and SQL Server Express set up folder permissions, service profiles and service start by default, so confirm them on the clean VM with the installer. These parts look correct:
- all 9 contexts share one unqualified `__EFMigrationsHistory` (`dbo` for the service login, not the module schema), and the ids carry the module name, so they cannot collide
- each migration creates its own schema (`EnsureSchema`), and no foreign key crosses modules, so the order in which `CrearBaseDeDatosAsync` migrates the contexts does not matter; EF 10 takes `__EFMigrationsLock`, so two processes starting together do not both migrate
- the generated SQL: 6 filtered unique indexes with valid T-SQL filters, `nvarchar(max)` for `TextoLargo` (8000 > 4000), `decimal(19,4)` everywhere, and deterministic seeds (fixed GUIDs, no clock), so `HasPendingModelChanges` stays stable
- migrations run before hosted services and Kestrel start, and `MigracionesTests` really fails on a model change without a migration (the 9 design-time factories are found by reflection and counted)
- the outbox has no "last seen" watermark, so identity values committed out of order are never skipped; with SQL Server's default locking READ COMMITTED the reader waits for an uncommitted outbox row; the first handler is idempotent (`ExecuteDelete` by `TurnoId`); the event-type map is now a DI singleton
- the chunk framing: the chunk number in the nonce stops reordering and dropped chunks, the authenticated last-chunk flag stops truncation at a chunk boundary, and GCM covers each chunk's length
- PBKDF2-SHA256 with 600,000 iterations (the OWASP 2023 figure), a 16-byte random salt, and the phrase itself never stored
- `BACKUP DATABASE @p0 TO DISK = @p1 WITH INIT, CHECKSUM` is valid T-SQL with variables (no injection, no `COMPRESSION`, which Express lacks), it does not run inside a transaction, and the service login owns the database, so it may back it up
- `/health` costs at most a few indexed queries and one directory listing.
